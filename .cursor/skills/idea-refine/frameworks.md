# Ideation Frameworks

Use selectively — pick the lens that fits the idea. Do not run every framework mechanically.

## How Might We (HMW)

Reframe problems as opportunities:

- "How might we help [user] achieve [outcome] without [pain]?"
- Bad: "How might we build a better spreadsheet?"
- Good: "How might we make duel results trustworthy without manual entry?"

## Jobs to Be Done

What is the user hiring this product to do?

- **Functional job:** The practical task (e.g., "record who won")
- **Emotional job:** How they want to feel (e.g., "settle the rivalry with confidence")
- **Social job:** How they want to be perceived (e.g., "be the organized friend in the group")

## First Principles

Strip away convention. Ask:

1. What do we know is true?
2. What are we assuming because "that's how it's done"?
3. If we started from zero today, what would we build?

## Pre-Mortem

Imagine the idea failed six months from now. Why?

- List 5 failure modes before building.
- For each, ask: "Can we detect this early? Can we prevent it?"

## Analogies & Cross-Domain

Borrow patterns from adjacent domains:

| Domain | Pattern | Question |
|--------|---------|----------|
| Sports | Box score | What stats matter after a duel? |
| Banking | Ledger + audit trail | How do we make records dispute-proof? |
| Social | Shared album | What makes a group want to contribute? |
| Gaming | Replay system | What evidence backs a logged result? |

## SCAMPER

| Letter | Lens | Prompt |
|--------|------|--------|
| S | Substitute | What could we replace (manual entry → auto-capture)? |
| C | Combine | What adjacent features merge naturally? |
| A | Adapt | What works elsewhere that we could borrow? |
| M | Modify | What if we made it smaller, faster, or weirder? |
| P | Put to other uses | Who else would use this unexpectedly? |
| E | Eliminate | What step can we remove entirely? |
| R | Reverse | What if the user flow ran backwards? |

## Opportunity Solution Tree

```
Outcome (measurable)
├── Opportunity 1 (user pain)
│   ├── Solution A
│   └── Solution B
└── Opportunity 2 (user pain)
    └── Solution C
```

Use when the idea is broad — map pains before jumping to solutions.

## Assumption Mapping

Plot assumptions on two axes:

- **Importance:** How much does the idea depend on this being true?
- **Evidence:** How much do we know today?

Prioritize validating **high importance, low evidence** assumptions first.

## MoSCoW (for MVP scoping)

- **Must have:** Without this, the idea doesn't work
- **Should have:** Important but not launch-blocking
- **Could have:** Nice if time allows
- **Won't have:** Explicitly out of scope (feeds the "Not Doing" list)
